# tracelens 使用指南

本文按「拿到一份 Trace 之后怎么用」的顺序组织。设计取舍见
[架构说明](架构.md)，实测数据见[自验报告](自验报告.md)。

## 0. 安装

```bash
uv sync --dev            # 开发
uv tool install .        # 作为独立命令行工具
```

openEuler 自带 python3，`pipx install tracelens` / `uv tool install tracelens`
会创建隔离虚拟环境并把命令挂到 PATH，不污染系统 Python。

## 1. inspect：先看一眼这是什么

```bash
tracelens inspect --input trace.json
```

```
文件      : trace.json
格式      : mlflow
trace_id  : 4bf92f3577b34da6a3ce929d0e0e4736
文件大小  : 3,973,892 字节
span 总数 : 411（根节点 1 个）
span 体积 : 3,970,689 字节，占文件 99.9%
整体状态  : ERROR，ERROR 节点 1 个
类型分布  : TOOL=361, MODEL=25, CHAIN=24, AGENT=1
类型来源  : Explicit=411
ERROR 节点:
  4fceb8ab TOOL      sql_query  relation "revenue_q3" does not exist
```

**「类型来源」这一行值得多看一眼。** 它告诉你节点类型是显式声明的（Explicit）、
按标准约定推出的（Convention）、还是拿 span 名猜的（Heuristic）。如果这里出现
大量 Heuristic，说明这份 Trace 的埋点语义不完整，后续基于类型写的规则要谨慎。

## 2. skeleton：生成骨架与索引

```bash
tracelens skeleton --input trace.json \
    --config examples/rules.toml \
    --format tree \
    --max-tokens 4000 \
    --out skeleton.txt \
    --emit-index trace.idx
```

| 参数 | 说明 |
| --- | --- |
| `--config` | 规则/配置 TOML；不给则用内置默认规则集 |
| `--format` | `tree`（默认，给 LLM）/ `json`（给程序）/ `md`（给人） |
| `--max-tokens` | token 预算，超出则逐级增压，见下文 |
| `--out` | 骨架输出文件；不给则打到 stdout |
| `--emit-index` | 同时写出字节偏移索引——**没有它就没法 expand** |
| `--detach <目录>` | 把每个 span 的原文物化一份，应对原文件会被轮转的场景 |
| `--strict-grapheme` | 按 grapheme cluster 截断（需 `[grapheme]` extra） |
| `--exact-tokens` | 用 tiktoken 精确计数（需 `[tokens]` extra） |

### 三种格式怎么选

- **tree**：默认。给 LLM 看，token 效率最高——同一份骨架比 json 省约 54% 的 token。
- **json**：给程序消费。schema 稳定、可 diff，适合做 CI 的比对基线。
- **md**：给人看，可直接贴进 PR 或 issue。

### `--max-tokens`：让骨架一定装得进预算

给定预算后，渲染前会估算体积，超预算则按既定次序逐级增压：

1. 收紧截断阈值（预览留得更短）
2. 降低展示详细度（先去掉 expand 命令行，再收起截断细节）
3. 折叠同类兄弟
4. 压缩展示深度

直到达标，或触及**保底集**（根节点 + ERROR 路径）——保底集不可再剪。

两点保证：**收紧只影响展示，不影响可取回性**——`span_id` 与字段路径始终在骨架里，
`expand` 永远有效；**达不到预算时不会假装成功**，骨架末尾会明写「已压到最紧仍超
预算」。

## 3. expand：按需取回原文

```bash
# 整个 span（span_id 支持短前缀，和 Git short hash 一样）
tracelens expand --input trace.json --index trace.idx --span-id 4fceb8

# 只取某个字段
tracelens expand --input trace.json --index trace.idx --span-id 4fceb8 \
    --field '$.attributes["mlflow.spanOutputs"]'

# 原始字节写 stdout（不加换行、不做编码转换），用于逐字节比对
tracelens expand --input trace.json --index trace.idx --span-id 4fceb8 --raw \
    > span.json

# 原文件不在场时，从 --detach 物化目录取
tracelens expand --index trace.idx --span-id 4fceb8 --detach spans/
```

### 字段路径语法

JSONPath 的一个自实现子集，够用即止：

```
$.a.b.c
$.a[0].b
$.attributes["mlflow.spanInputs"]     ← key 里含点号时用方括号形式
```

带引号的段用**双引号**，这样整条 `--field` 参数可以安全地被 shell 的单引号包住。
骨架里的 `expand:` 提示行可以直接复制粘贴执行。

`--field` **不是**「解析整个 span 再把字段值重新序列化」——那会破坏字节承诺。
实现是对该 span 的切片做一次带路径追踪的二次扫描，定位目标字段值自身的字节区间，
返回的仍是原文件字节。

## 4. 写规则

完整的带注释样例见 [examples/rules.toml](../examples/rules.toml)，
更激进的大 Trace 示例见 [examples/demo_rules.toml](../examples/demo_rules.toml)。

### 求解语义

所有规则按 `priority` **降序**排序后逐条尝试，**首匹配生效**；同 priority 保持
声明顺序。没有命中任何规则的 span 取默认动作 `keep`。

一条规则里的多个 `match` 条件是**与**关系；`match` 为空表示匹配一切。

### 四种动作

| 动作 | 效果 |
| --- | --- |
| `keep` | 保留。被规则**显式** keep 的节点，其到根的整条祖先链会被强制保留 |
| `drop` | 删除节点自身；存活后代重挂到最近存活祖先并标记折叠层数，节点自身进入同类占位节点的计数 |
| `collapse_subtree` | 保留节点，但把它的整棵子树折叠成占位节点 |
| `truncate` | 保留节点，按 `params` 截断它的大体积字段 |

「显式 keep 会保护祖先链」这条容易忽略但很重要：它是「我关心这个节点」的强信号。
反过来，未命中规则的隐式保留**不会**保护祖先链，否则 `drop` 将永远不触发重挂。

### 匹配条件

`name_glob`、`kind`、`kind_source`、`status`、`min_bytes` / `max_bytes`、
`min_depth` / `max_depth`。

`kind_source` 常用于「只对类型是猜出来的节点特殊处理」，例如：

```toml
[[rules]]
name = "启发式判定的节点一律保留，避免误剪"
action = "keep"
priority = 90
match = { kind_source = "Heuristic" }
```

### 截断策略

| 策略 | 适用 |
| --- | --- |
| `head` | prompt——系统指令在开头 |
| `tail` | 错误栈——根因在结尾 |
| `head_tail` | 工具输出——开头是格式说明、结尾是结论 |

### 无法关闭的硬保护

无论规则怎么写：根节点永不剪除；任一 ERROR 节点到根的整条路径永不剪除。
这两条写死在引擎里，不在默认规则集里，用户配置改不掉。

## 5. 四层配置

```
内置默认  <  TOML 文件  <  环境变量 TRACELENS_*  <  CLI 参数
```

配置项与规则集写在同一个 TOML 文件里：

```toml
format = "tree"
max_tokens = 4000
chars_per_token = 4.0
strict_grapheme = false
exact_tokens = false

[[rules]]
action = "drop"
match = { kind = "TOOL", status = "OK", max_bytes = 512 }
```

环境变量：`TRACELENS_CONFIG`（配置文件路径）、`TRACELENS_FORMAT`、
`TRACELENS_MAX_TOKENS`、`TRACELENS_CHARS_PER_TOKEN`、`TRACELENS_STRICT_GRAPHEME`、
`TRACELENS_EXACT_TOKENS`。

## 6. 典型排查流程

```bash
# ① 生成骨架与索引
tracelens skeleton --input trace.json --config rules.toml \
    --max-tokens 4000 --out skeleton.txt --emit-index trace.idx

# ② 把 skeleton.txt 交给 Agent（或自己读），定位可疑节点
#    重点看：唯一的 ERROR 节点、⚠ 标记的可疑类型、体积异常大的 MODEL span、
#           以及「父节点 OK 但子节点 ERROR」这类结构性异常

# ③ 对可疑节点取证
tracelens expand --input trace.json --index trace.idx --span-id <前 6 位>

# ④ 顺着数据流往下追，确认影响面
tracelens expand --input trace.json --index trace.idx --span-id <下游 span> \
    --field '$.attributes["mlflow.spanInputs"]'
```

第 ② 步里的「父节点 OK 但子节点 ERROR」值得单独强调：这类**结构性异常**只在保留
了完整拓扑的骨架上可见——它不在某一段文本里，它在结构里。任何基于「截断前 N 个
字节」的方案都拿不到这个信号。

## 7. 在脚本里判断结果

```bash
tracelens expand --input trace.json --index trace.idx --span-id "$id" > span.json
case $? in
  0) echo "取回成功" ;;
  2) echo "这个 span 不存在" ;;
  3) echo "原文件变了，索引作废——需要重新生成" ;;
  *) echo "其他错误" ;;
esac
```

区分「没找到」和「数据坏了」是刻意设计的：前者说明查错了 id，后者说明整份索引
都不能再信任了，处理方式完全不同。
