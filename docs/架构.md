# tracelens 架构说明

> 本文说明模块划分、数据流与关键设计约束。
> 测试设计与实测数据见[测试方案](测试方案.md)、[验证报告](验证报告.md)。

## 0. 采集层（可选，位于分析流程上游）

tracelens 的核心消费的是**标准 MLflow 形态的 trace.json**；trace 从哪来由采集层决定，
与分析层（ingest/prune/index/render）解耦：

```
opencode 会话（运行时已记录每次 LLM/工具调用的真实输入输出与错误）
      │  opencode-plugin/（方案 A，Node/TS，零运行时依赖）
      ▼
<项目>/.tracelens/traces/<会话>.trace.json   ← 标准 MLflow 形态
      │
      ▼
（进入下方数据流）
```

插件监听 `session.idle`，用 SDK `client.session.messages` 拉取会话全量消息/部件后组装：
会话 → 根 `AGENT`；每个 assistant 消息 → 一轮 `LLM`；轮内 `tool` part → `TOOL`
（`state.status==="error"` → `status_code=ERROR` + `status_message`）。插件与 Python 包
互相独立：插件在 `opencode-plugin/`，不进入本包的依赖图。

## 1. 数据流

```
raw trace.json (mmap 只读，全程按 bytes 记账)
      │
      ├─► ingest.sniff    读头部若干 KB，判定 MLflow / OTLP，定位 spans 数组位置
      ├─► ingest.scanner  字节级扫描（正则 search + bytes.find，C 速度）
      │        输出 Iterator[(span_start, span_end)]  ← 每个 span 对象的字节区间
      ├─► ingest.mlflow / ingest.otlp
      │        逐 span json.loads(mm[s:e]) → 抽元数据 → SpanMeta（用后即弃）
      │
      ├─► prune  (规则匹配 → keep / drop / collapse / truncate，拓扑重建)
      │
      ├─► render ──► skeleton.txt / .json / .md   (~KB，给 Agent 读)
      └─► index  ──► trace.idx  (struct 编码，span_id → offset,len)
                          │
                          └─► expand: mm[off:off+len] ──► 原样字节，逐字节一致
```

## 2. 模块划分与依赖纪律

| 模块 | 职责 |
| --- | --- |
| `model.py` | IR 定义（dataclass），**零内部依赖** |
| `errors.py` | 异常类型与退出码语义 |
| `ingest/scanner.py` | 字节级 JSON 扫描器：只识别边界，不解析值 |
| `ingest/sniff.py` | 格式嗅探 + spans 数组定位 |
| `ingest/kinds.py` | SpanKind 分级推断 + KindSource 标记 |
| `ingest/mlflow.py`、`ingest/otlp.py` | 两个 ingest 适配器 |
| `ingest/reader.py` | mmap + 嗅探 + 扫描 + 适配器的组装 |
| `prune/` | 规则、求解、拓扑重建、截断、点路径 |
| `index/` | 索引编解码与读路径（magic + 版本 + 原文件摘要 + 定长 entry） |
| `render/` | tree / json / md 三种骨架形态，以及 `--max-tokens` 的预算收紧循环 |
| `tokens.py` | token 估算与精确计数，始终标注用的是哪种方法 |
| `config.py` | 四层配置叠加 + pydantic 校验 |
| `cli.py` | 子命令组装 |
| `testkit.py` | 合成 Trace 生成器 |

所有模块只单向依赖 `model`，彼此不依赖，由 `cli` 负责组装。
将来的 `mcp_server.py` 与 `cli.py` 平行放置，核心零改动。

## 3. 三条硬约束

### 3.1 字节级一致是构造性的，不是靠测试保证的

`expand` 执行的就是 `mm[off:off+len]`，中间没有解析与再序列化环节——
想违反一致性都没有代码路径可走。测试只是加固，不是正确性的来源。

反过来说，任何「解析成对象 → 存起来 → 展开时再序列化」的做法都过不了这一关：
`json.dumps` 默认 `ensure_ascii=True` 会把中文写成 `\uXXXX`，键间空白会丢，
`2.50` 变成 `2.5`，重复 key 被静默吞掉。所以数据通路上**原始字节从不经过
loads→dumps 往返**；`loads` 只用于「解析单个 span 提取元数据、用完即弃」
这一条只读路径。

### 3.2 偏移记账单位强制为 bytes

`len("中") == 1` 但它在 UTF-8 里占 3 字节。任何环节把 `str.find` 的结果当字节
偏移写进索引，`expand` 都会切出错位垃圾。因此 str 只出现在「单字段截断」这类
局部只读操作里，其产物不回写偏移。

### 3.3 不确定的信息必须标注来源

`SpanKind` 携带 `KindSource`（Explicit / Convention / Heuristic / Unknown）。
下游读者是 LLM，把猜测伪装成事实会让它沿着错误的类型判断走错整条排查路线，
且错得毫无征兆。不知道就说不知道。

## 4. 扫描器的双模式状态机

字符串**外**：用编译好的正则 `search(buf, pos)` 一次 C 级扫描跳到下一个结构字符
（`"` `{` `}` `[` `]`），维护深度与容器类型，在 spans 数组层级记录每个元素对象的
进入/退出位置。

字符串**内**：切换模式，用 `buf.find(b'"', pos)` 直接跳到下一个引号，命中后向前
回看连续反斜杠的个数——奇数个说明这个引号被转义、仍在字符串里，偶数个才是字符串
结束。

这样 Python 层只处理稀疏的结构事件，重活全在 C 实现里。一个 100 MB 的 prompt
字符串在这里是一次内存搜索，而不是一亿次循环。

实测吞吐（Apple Silicon，200 MB 合成 MLflow trace）：**833 MB/s**，验收线是 200 MB/s。
完整的性能数据见[验证报告](验证报告.md)第五节。

## 5. 退出码

| 码 | 含义 |
| --- | --- |
| 0 | 成功 |
| 1 | 输入不存在或解析失败 |
| 2 | `span_id` 未命中 |
| 3 | 索引与原文件不匹配（摘要校验失败） |
| 4 | 配置非法 |

上层脚本与 Agent harness 必须能程序化地区分「没找到」和「数据坏了」。

## 6. 预算收紧与展示详细度

`--max-tokens` 给定预算后，按既定次序逐级增压：收紧截断阈值 → 降低展示详细度
（`Skeleton.detail`：2 完整 / 1 紧凑 / 0 最简）→ 折叠同类兄弟 → 压缩展示深度，
直到达标或触及保底集（根节点 + ERROR 路径）。

两条硬约束：

* **收紧只影响展示，不影响可取回性**——`span_id` 与字段路径始终在骨架里，
  截断标记的 `digest` 与 `expand_hint` 一概不动。
* **达不到预算时不假装成功**——返回压到最紧的版本，并在骨架末尾明写
  「已压到最紧仍超预算」。

这一层与剪枝阶段的区别：剪枝改变的是「骨架包含哪些节点」，受五条不变量约束；
预算收紧是展示层的进一步压缩，会如实记录压到了第几级。
