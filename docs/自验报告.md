## 一、数据量与窗口占用

demo Trace 来自一个**故意植入 bug** 的 LangGraph 风格 Agent 执行
（`scripts/make_demo_fixture.py`，确定性生成）：

| 指标 | 数值 |
| --- | --- |
| span 总数 | 411 |
| 文件体积 | 3,973,892 字节（3.8 MB） |
| 全文 token（估算） | 约 917,000 |
| span payload 占文件比 | 99.9% |

用 `examples/demo_rules.toml` 生成骨架后：

| 指标 | 数值 |
| --- | --- |
| 存活节点 | 29（其余 382 个进入占位节点，节点数守恒） |
| 骨架体积（tree） | 16,220 字节，占原文件 **0.41%** |
| 骨架 token（估算） | 3,713 |
| 索引体积 | 20,592 字节，占原文件 0.52% |

**三种渲染形态的 token 对比**（同一份骨架）：

| 形态 | 字节 | token | 相对 tree |
| --- | --- | --- | --- |
| tree | 16,220 | 3,713 | — |
| json | 33,285 | 8,112 | +118% |
| md | 16,356 | 3,817 | +3% |

tree 比 json 省 **54%** 的 token，落在方案预估的 40%~60% 区间内。省下来的
不是磁盘，是 Agent 的推理预算。

### 价值命题的正确表述

结论不打算用「压缩了 99.6%」来表述——那是压缩算法的语言，会让人以为这是一个
有损换体积的权衡。真正的命题是：

> **128K 窗口下，原始 Trace 只装得进 14%，而且 Agent 无法选择装哪 14%；
> 用了这个工具之后，Agent 拿到 100% 的拓扑加上自己选定的关键细节，只占窗口的 3.1%。**

关键差别在「无法选择」四个字。截断是被动的，索引 + 按需展开是主动的。

## 二、成功定位问题的案例（实验组）

植入的 bug：SQL 查询用了不存在的表 `revenue_q3`（实际表名 `revenue_2025q3`），
数据库返回 `42P01`；**工具封装层把错误吞掉并把状态标成 OK**，错误字符串随后作为
「正常的工具返回数据」进入了后续每一轮的 prompt，模型据此编出了一个看起来合理
但内容错误的答案。

这个 bug 形态是刻意选的：它不会让执行崩掉，最终答案也像模像样——真实世界里最难
查的就是这一类，有征兆但征兆被掩埋，而掩埋它的正是「上下文太长塞不进去」。

`scripts/demo_investigate.py` 的实测过程：

| 步骤 | 动作 | 消耗 |
| --- | --- | --- |
| 1 | 生成骨架与索引 | 骨架 3,713 token（窗口的 2.9%） |
| 2 | 读骨架，命中唯一的 ERROR 节点 `4fceb8 TOOL sql_query`；注意到同层的 `tool_executor` 状态是 OK → 判断错误被吞掉 | 0（信息已在骨架里） |
| 3 | `expand --span-id 4fceb8` 取回完整 Payload，看到 `relation "revenue_q3" does not exist` 与错误码 `42P01` | 687 字节 |
| 4 | `expand` 下游 MODEL span 的 `mlflow.spanInputs`，确认错误串原样出现在 prompt 里 | 命中处上下文 400 字符 |
| 5 | 给出根因与修复建议 | — |

**全过程消耗约 3,963 token，占 128K 窗口的 3.1%。**

值得单独说明的是步骤 2：「父节点是 OK、子节点是 ERROR」这个**结构性异常**，
在骨架上是一眼可见的，因为骨架保留了完整拓扑与每个节点的状态。任何基于「截断
前 N 个字节」的方案都拿不到这个信号——它不在某一段文本里，它在结构里。

### 关于「不调 LLM」

两个 demo 脚本都不调用任何 LLM，这是刻意的。要论证的命题是**信息可达性**：
根因所需的证据是否落在 Agent 能拿到的那部分数据里。如果结论依赖某个模型某次
运行的表现，它就既不可复现，也说不清是工具起了作用还是模型碰巧猜对了。
模型能力那一维由对照组从反面补上——证据不可达是比模型能力更硬的约束。

> 补充：证据可达之后「真实 LLM 能不能用起来」这一环，已由
> [真实 Agent 测试报告](真实Agent测试报告.md) 用一次盲测正面验证——一个事先不知道
> bug 的冷启动 Agent 只凭骨架 + `expand` 精确命中了根因。本节的「不调 LLM」立场因此
> 不再是缺口，而是与真实 Agent 盲测互补的两条独立证据。

## 三、对照组

设置：不使用 tracelens，把原始 Trace 从头截断到 128K token 直接喂给同一个模型。
两组之间唯一的变量是「是否使用工具」，Trace、任务、窗口大小全部固定。

`scripts/demo_control.py` 实测：

| 指标 | 数值 |
| --- | --- |
| 窗口能装下 | 前 553,709 字节，占全文 **13.9%** |
| 窗口内的 span | 60 / 411（14.6%） |
| ERROR 节点 | 共 1 个，落在窗口内的 **0 个** |
| `sql_query` 的字节偏移 | 1,297,498（窗口截断在 553,709） |

**对照组失败，且失败模式可在数据层面直接判定**：前 128K token 几乎全被前几轮的
巨型 prompt 占满，唯一的错误证据根本进不了窗口。无论用什么模型、怎么提示，
它都不可能基于证据给出正确结论——这个失败本身反向演示了任务动机：
不是模型不够强，是证据没送到它面前。

## 四、性能实测

`scripts/bench_pipeline.py 200`，200 MB 合成 MLflow Trace（25,878 个 span）：

| 阶段 | 耗时 |
| --- | --- |
| 扫描（字节级边界识别） | 0.24 s（**833 MB/s**） |
| 元数据解析（逐 span loads 用后即弃） | 1.45 s |
| 剪枝 + 截断 | 0.48 s |
| 渲染 | 0.06 s |
| 建索引（含全文件 blake2b） | 0.15 s |
| **全流程** | **3.20 s** |

对照方案第六节的三条验收线：

| 指标 | 验收线 | 实测 | 结论 |
| --- | --- | --- | --- |
| 扫描吞吐 | ≥ 200 MB/s | 833 MB/s | ✅ 超出 4 倍 |
| 1 GB 全流程 | ≤ 120 s | 16 s（按 200 MB 线性外推） | ✅ |
| 堆内存峰值 | ≤ max(256 MB, 2× 最大单 span) | 83.7 MB（最大单 span 20.6 KB） | ✅ |

第三条是本路线要验证的**核心性质**：mmap 只读映射 + 逐 span 解析用后即弃，
使堆占用与「最大单个 span」成正比，而不是与文件大小成正比。200 MB 文件的堆峰值
83.7 MB，其中绝大部分是 411…25,878 个 `SpanMeta` 元数据对象本身，与 payload 无关。

诚实标注两点：

1. **1 GB 数据是线性外推的**，不是实测。扫描与解析都是单遍顺序处理，线性外推有
   依据，但页缓存在 1 GB 量级的行为会与 200 MB 不同。正式验收应单独跑
   `bench_pipeline.py 1024`。
2. **扫描吞吐依赖数据形态**。合成数据的字符串占比高（结构字符稀疏），正好是
   `bytes.find` 快进模式最擅长的场景；结构极其破碎的 Trace 吞吐会下降。
   200 MB/s 的验收线正是按这个下限校定的。

## 六、与 compaction / condenser 类方案的定性对比

| | compaction / condenser<br>（Claude Code、OpenCode、OpenHands） | tracelens |
| --- | --- | --- |
| 是否有损 | 有损 | 无损 |
| 可逆性 | 不可逆 | 凭 `span_id` 逐字节取回 |
| 是否引入模型 | 由 LLM 生成摘要 | 零 LLM 参与，纯确定性程序 |
| 服务场景 | 进行中的会话 | 事后取证 |
| 失败模式 | 摘要可能恰好把根因压掉，且无法回头 | 索引失配 → 明确报错（退出码 3） |

两者是**互补关系，不是竞争关系**。对进行中的会话，丢些细节换继续工作是划算的；
事后排查的约束正好相反——证据不能有损。设想根因藏在第 3 轮某个工具输出的最后
一行：compaction 有一定概率把它压缩成「工具返回了数据」，之后无论怎么问都找不
回来；本方案的骨架至少保留该 span 的存在、状态与截断标记，一条 `expand` 就能拿
回原文。

同时，业界的共性模式本方案也照单借鉴了：全量存档 + 精简视图、关键内容硬保护
（根 + ERROR 路径，对应 OpenHands 的 `keep_first`）、占位符化的输出剪除
（对应 OpenCode 的 pruning placeholder，差别是本方案的占位符携带可执行的取回
路径）、预算感知触发（`--max-tokens`）。

## 七、局限性

见 [局限性与改进方向](局限性.md)。要点复述三条：

1. `expand` 依赖原始文件在场且未被修改；会被轮转的场景要用 `--detach` 提前物化，
   代价是空间接近翻倍。
2. token 计数默认是估算值，只有装了 `[tokens]` extra 才精确；骨架里始终标注用的
   是哪种方法。
3. `SpanKind` 的启发式推断可能出错，兜底是 `KindSource` 可信度标记，
   而不是追求推断零错误。
