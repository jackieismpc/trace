# tracelens 真实 Agent 测试报告

> 本报告补上了 [自验报告](自验报告.md) 明确留下的空白：**把一个真实的 LLM Agent
> 放进回路里**。自验报告的两个 demo 脚本刻意不调用任何 LLM（只论证「信息可达性」），
> 因此始终没有回答一个问题——**当证据确实可达时，一个真实的、事先不知道答案的
> Agent，到底能不能只凭骨架 + 按需展开把根因查出来？**
>
> 本次测试用一次**盲测**回答了它：是。
>
> 测试执行者：Claude（Opus）负责设计与评分，两个**冷启动的 Claude Sonnet 子 Agent**
> 分别扮演实验组与对照组的排障工程师。
> 报告日期：2026-07-23。全部命令与产物可原地复现（见文末「复现」）。

---

## 一、一句话结论

在一份 3.79 MB / 411 span、根因被**故意隐藏且连测试设计者都事先不知道**的 Trace 上：

- **实验组**（冷启动子 Agent，只有 16 KB 骨架 + `tracelens expand`）：**完全命中根因**
  ——精确到 span_id、错误原文、错误码、掩盖机制、传播链，全过程数据足迹 **13,078
  token（占 128K 窗口的 10.2%、占全文的 1.13%）**。
- **对照组**（同款冷启动子 Agent，拿到截断进 128K 窗口的原始 JSON）：**无法定位根因**
  ——窗口里 57 个 span、0 个 ERROR，根因落在窗口外的第 3,129,145 字节处；子 Agent
  自己诚实地判定「证据不在可见范围内，无法给出确定结论」。

两组之间唯一的变量是「是否使用 tracelens」。结论不是「模型不够强」——**两组是同一个
模型**——而是「证据有没有送到它面前」。

---

## 二、为什么要做这次测试

自验报告第二节末尾写得很清楚：

> 「两个 demo 脚本都不调用任何 LLM，这是刻意的……如果结论依赖某个模型某次运行的
> 表现，它就既不可复现，也说不清是工具起了作用还是模型碰巧猜对了。」

这个立场是对的——**信息可达性**是比模型能力更硬的约束，应该先钉死。但它也留下一个
没被验证的环节：骨架的设计目标是「给 LLM 读」，而从没有 LLM 真的读过它。骨架里那些
符号（`✂ ⚠ ⋯`）、那行写在数据里的 `expand:` 提示、那个「父 OK / 子 ERROR」的结构
信号——**这些是不是真的能被一个 LLM Agent 利用起来**，只能靠把 LLM 放进回路来验证。

本报告就做这件事，并且用盲测把「工具起了作用」和「模型碰巧猜对」这两种解释区分开。

## 三、盲测协议（可信度是怎么保证的）

一个显而易见的质疑：报告的执行者（Claude）如果知道答案，评分就不可信。为此设计了如下
协议，逐条堵住信息泄露：

1. **根因由运行时熵随机选定，不是写死的。** 新写的生成器
   [`scripts/blind_bug_fixture.py`](../scripts/blind_bug_fixture.py) 用 `os.urandom(8)`
   取种子，在 4 个根因原型 × 各自的候选参数 × 触发轮次（8~20 轮随机）× 随机 span_id
   之间随机组合。设计者读得到代码（知道 bug 的**空间**），但读不到这一次具体抽中了
   哪个实例。
2. **答案当场密封。** 生成器把标准答案写入
   `out/blind_answer_key.SEALED.json`，设计者承诺在两个子 Agent 交卷之前不打开它。
3. **设计者全程不看骨架内容。** 生成骨架/索引、切对照组截断文件，全部用只写不读的
   命令完成（`skeleton --out`、`head -c`）；`inspect` 会打印 ERROR 节点，因此**没有
   对盲测 Trace 运行过 inspect**。生成器 stdout 只打印非泄露统计（span 数、体积、
   根因**字节偏移**——只暴露位置不暴露内容）。
4. **被测者冷启动。** 两个子 Agent 是独立的新上下文，除了各自拿到的文件和同一句任务
   描述，对 bug 一无所知。
5. **交卷后才开封评分。** 读取密封答案，对照两份诊断逐字段打分，并**独立复跑**实验组
   声称的每一条 `expand`，用 blake2b 校验它没有编造。

这次实际抽中的实例（开封后揭晓）：原型 `missing_config_key`，第 20 轮，内层工具
`load_dataset` 报 `KeyError: config key 'FINANCE_PATH' is not set`，被外层
`config_loader` 吞掉标成 OK。**设计者在两个子 Agent 交卷前确实不知道这些。**

## 四、被测 Trace 的数据画像

| 指标 | 数值 |
| --- | --- |
| span 总数 | 411 |
| 文件体积 | 3,972,199 字节（3.79 MB） |
| 全文 token（tiktoken cl100k_base） | **1,154,189** |
| 根因 span 字节偏移 | 3,129,145 |
| ERROR 节点 | 1 个（内层 `load_dataset`） |

体积分布与真实 Agent Trace 一致：每轮 MODEL 调用携带全量历史，随轮次近似平方级膨胀，
少数 MODEL span 贡献绝大部分字节，而拓扑信息占比不到 1%。**128K 窗口只装得下全文的
11.1%**，且装的是「头部」——最没用的前几轮巨型 prompt。

## 五、实验组：冷启动子 Agent，只有骨架 + expand

**给到的东西**：16 KB 骨架文件、`tracelens expand` 命令、以及一句限制——「原始
3.8MB JSON 塞不进上下文，本次严禁直接读取」。**没有**给原始数据。

**它的实际过程**（真实执行，非臆测）：读骨架 → 一眼锁定唯一的 ERROR 节点，并注意到它
的兄弟节点 `config_loader` 状态是 OK（结构性异常）→ `expand` 取回根因 span 确认错误
原文 → 顺着数据流 `expand` 下游 MODEL 的 `spanInputs`，确认错误串原样进入了后续
prompt → `expand` 最终答案，确认它是基于被污染上下文编出来的。

**它交出的诊断 vs 密封答案（开封评分）**：

| 字段 | 密封标准答案 | 子 Agent 诊断 | 命中 |
| --- | --- | --- | --- |
| 根因 span_id | `f61c23699371208d` | `f61c23699371208d` | ✅ 精确 |
| 名称 / 类型 / 状态 | load_dataset / TOOL / ERROR | 完全一致 | ✅ |
| 错误原文 | `KeyError: config key 'FINANCE_PATH' is not set` | 逐字一致 | ✅ |
| 错误码 | `KeyError` | `KeyError` | ✅ |
| 外层封装 span | `6b7005…` config_loader（OK） | `6b7005` config_loader，识别为「漂白」层 | ✅ |
| 触发轮次 | 第 20 轮 | turn_20 | ✅ |
| 传播机制 | 内层 ERROR → 外层标 OK 把错误当结果 → 进入每轮 prompt → 编造答案 | 逐环命中，且指出违反了系统提示词硬约束 | ✅ |
| 修复方向 | 配置键名过时（应为 `FINANCE_PATH_CURRENT`） | 指出配置缺失 + 封装层吞错 + CHAIN 不冒泡 + 答案生成前应加闸门 | ✅（见下注） |

> 注：标准答案里「正确键名是 `FINANCE_PATH_CURRENT`」这一条**不在 Trace 数据中**
> （Trace 只记录了 `FINANCE_PATH` 失败，没记正确名是什么），任何 Agent 都无法从
> 数据推出来。子 Agent 在**证据允许的范围内**给出了完整且正确的诊断，并额外指出了
> 4 个系统级修复点。这是「诚实标注证据边界」，不算漏判。

**数据足迹**（本次调查真实消耗）：

| 项 | token |
| --- | --- |
| 骨架 tree | 5,467 |
| 10 次 expand 累计（24,373 字节） | 7,611 |
| **合计** | **13,078**（占 128K 窗口 **10.2%**，占全文 **1.13%**） |

一个值得如实记录的观察：子 Agent 有两次 `expand` 直接取了完整的 MODEL prompt
（9.7 KB、11.7 KB），若改用 `--field ... head` 只取命中处片段还能更省。即便如此，
13K token 相对全文 1.15M token 仍是零头。**工具没有强迫它省，是数据结构让「省」成了
默认路径。**

**一个额外发现**：这次根因的错误串其实**直接印在 16 KB 骨架里**（因为规则对 ERROR
节点是 `keep` 全文）：

```
   │  ├─ b0e11f CHAIN     turn_20                           OK    3.5s
   │  ├─ 037608 MODEL     gpt-4o                            OK    2.1s  in=9.3K   out=164  ✂
   │  ├─ f61c23 TOOL      load_dataset                   ERROR   200ms  in=65     out=89
   │  │  └─ error: KeyError: config key 'FINANCE_PATH' is not set
   │  ├─ 6b7005 TOOL      config_loader                     OK   210ms  in=68     out=66
   │  └─ ⋯ elided 14 similar TOOL spans (all OK)
```

「子 ERROR 紧挨着兄 OK」这个信号不在任何一段文本里，它**在结构里**——任何「截断前 N
字节」的方案都拿不到它。骨架把它一眼呈现出来，`expand` 再把细节逐字节坐实。

## 六、对照组：同款子 Agent，窗口内的原始 JSON

**给到的东西**：原始 Trace 从头截断到 512,000 字节（≈128K token，正好填满窗口），
一句说明——「这是把 trace 塞进上下文后、超出窗口被硬截断的那部分，请据此诊断」。这
精确复刻了「把 Trace 直接喂给模型」的常规做法。

**它交出的结论**（真实执行）：

- 窗口内共 **57 个 span**，`status_code` 只出现 `"OK"`（**57 次**），`"ERROR"`
  **0 次**，全文检索关键词 `error` **命中 0 次**。
- 窗口只覆盖了 24 轮里的前 3.1 轮（约 13% 的 span），第 4 轮在第 3 个工具调用处被硬
  截断，第 5~24 轮（约 355 个 span，**含根因所在的第 20 轮和产出最终答案的那一轮**）
  完全缺失。
- **诚实评估**：「不能确定根因……产出最终答案的那一轮压根不在可见窗口里。」它只能
  定性指出一个可疑诱因（工具输出被低信息量套话稀释、根因被挤出窗口），**给不出确定
  的根因 span、错误原文或错误码**。

对照组失败，且**失败模式在数据层面可直接判定**：根因在第 3,129,145 字节，窗口在
512,000 字节处就截断了。无论换什么模型、怎么提示，它都不可能基于证据给出正确结论。
这个失败本身反向印证了任务动机：不是模型不行，是证据没送到。

值得一提的是，对照组子 Agent 没有幻觉——它**正确地诊断出了自己的失败模式**，而不是
硬编一个看似合理的答案。这恰恰说明幻觉风险来自「证据缺失又被迫作答」，而 tracelens
消除的正是「证据缺失」这一前提。

## 七、两组同题对比

| 维度 | 实验组（tracelens） | 对照组（截断进窗口） |
| --- | --- | --- |
| 拿到的拓扑 | 100%（411 → 29 存活 + 占位，节点数守恒） | 14%（57/411），且只有头部 |
| 看得到 ERROR 节点 | 是（唯一 1 个，一眼可见） | 否（窗口内 0 个 ERROR） |
| 根因定位 | **精确命中** span_id + 错误原文 + 传播链 | **无法定位**，根因在窗口外 |
| 数据足迹 | 13,078 token（窗口的 10.2%） | 148,997 token（填满窗口）仍失败 |
| 细节可选 | 主动，凭 span_id 逐字节按需取 | 被动，只能吃被截断后剩下的 |
| 输出可信度 | 有据可查，可逐条复核 | 诚实判定「证据不足」（未幻觉） |

「无法选择装哪部分」是对照组的死穴：截断是被动的，索引 + 按需展开是主动的。

## 八、工具正确性与边界验证

除了端到端的排障效果，还独立验证了四条设计承诺是否名副其实。全部通过：

**① 还原 Payload 与原文逐字节一致（构造性，非靠测试）。** 独立复跑实验组对根因 span
的 `expand`，输出 699 字节；在原文件中定位到同一段字节（第 3,129,145 位），
blake2b 摘要 `db2cac4a502ae104` 与原文切片**完全一致**，`expand输出 == 原文切片`
返回 `True`。`expand` 执行的就是 `buf[offset:offset+length]`，没有解析/再序列化环节。

**② 宁可失败也不喂错数据（退出码 3）。** 把 Trace 复制一份、篡改第 200 字节的 1 个
字节，再 `expand`：立即以**退出码 3** 报错，并打印「索引记录的摘要 vs 当前文件摘要」
不一致，而不是返回一段错位的垃圾切片。

**③ 「没找到」和「数据坏了」可程序化区分（退出码 2）。**
- `--span-id zzzzzz`（不存在）→ **退出码 2**，「未找到 span_id」。
- `--span-id f`（歧义短前缀）→ **退出码 2**，并列出「匹配到 24 条」及候选，引导补长。

**④ 字段级 expand 精确定位。** `--field "$.attributes['mlflow.spanOutputs']"` 只取回
该字段的原始字节：`{"error": "KeyError: config key 'FINANCE_PATH' is not set", "code":
"KeyError"}`，无需取整个 span。

**⑤ 硬保护：ERROR 到根的整条路径永不被剪。** 尽管 `demo_rules.toml` 激进地折叠了
345 个 TOOL、23 个 CHAIN，程序化检查确认：根因 span（`f61c23`）、外层封装
（`6b7005`）、所在轮 `turn_20`、根节点 `research_agent` **全部保留在骨架中**。排查最
需要的两样东西（根 + ERROR 路径）由代码保证，不交给配置。

## 九、渲染形态的 token 成本

同一份骨架、三种渲染（tiktoken cl100k_base 实测）：

| 形态 | 字节 | token | 相对 tree |
| --- | --- | --- | --- |
| tree | 16,247 | **5,467** | — |
| json | 33,314 | 9,512 | +74% |
| md | 16,390 | 5,933 | +9% |

tree 比 json **省 43% token**，落在方案预估的 40%~60% 区间内。给 Agent 读用 tree
是划算的默认；需要机器再解析时才用 json。

## 十一、局限与诚实标注

1. **一次抽样，不是统计分布。** 本报告是**一个**随机实例上的一次盲测，抽中的是
   `missing_config_key` 原型。要给出「成功率」需在多个随机种子、四个原型上各跑多次
   并统计——这是自然的后续工作，生成器已支持（每次运行自动换种子）。本次的价值在于：
   在一个设计者事先不知道答案的实例上，跑通了「真实 LLM + 骨架 + expand」的完整闭环。
2. **实验组的「禁读原文」是指令约束。** `expand` 需要 `--input` 指向原文件，因此技术上
   子 Agent 能 `cat` 它——靠的是明确指令 + 「3.8MB 会撑爆自己上下文」的自然威慑。已在
   审计中确认它没有违规。要做成硬隔离可用 `--detach` 物化后回收原文件。
3. **四个原型共享同一种「静默失败」结构**（内层 ERROR、外层吞掉）。这是刻意的——它保证
   骨架上的结构信号一致，把「错在哪、错的内容、如何传播」作为被盲查的未知量。对「完全
   没有 ERROR 状态、纯靠数值错误」的根因（如单位换算错误），本工具只能保留拓扑与可展开
   性，判定仍需 Agent 的数值推理，不在本次覆盖范围内。
4. **token 计数用 cl100k_base**，与目标模型的分词器可能有差异；量级结论（1.15M vs
   13K）不受影响。

---

## 十二、结论

自验报告钉死了「证据可达」，本报告钉死了「可达的证据能被真实 Agent 用起来」。合起来，
tracelens 的价值命题在**回路里**得到了验证：

> 一个事先不知道答案的真实 LLM Agent，只用 16 KB 骨架 + 按需 `expand`，在一份 3.79 MB、
> 根因埋在第 300 万字节的 Trace 上，用全文 1.13% 的数据足迹**精确定位了根因**；同一个
> 模型在「把 Trace 截断进窗口」的常规做法下，因为证据落在窗口外而**无法定位**。

差别不在模型，在于证据有没有以「高密度、可寻址、可无损取回」的形态送到模型面前。这正是
这个工具做的事。

## 复现

```bash
# 1) 造一份根因随机且密封的盲测 Trace
python scripts/blind_bug_fixture.py out/blind_trace.json out/blind_answer_key.SEALED.json

# 2) 生成骨架 + 索引（不看内容以保持盲测）
tracelens skeleton --input out/blind_trace.json --config examples/demo_rules.toml \
    --format tree --max-tokens 4000 --out out/blind_skeleton.tree --emit-index out/blind.idx

# 3) 对照组：截断到 128K 窗口
head -c 512000 out/blind_trace.json > out/blind_control_head.json

# 4) 分别把骨架、截断文件交给两个冷启动 Agent，收集诊断，再开封 SEALED 评分
#    边界验证：
tracelens expand --input out/blind_trace.json --index out/blind.idx --span-id <ERROR前6位> --raw   # 字节一致
tracelens expand --input <改过1字节的副本> --index out/blind.idx --span-id <...>                   # 退出码 3
tracelens expand --input out/blind_trace.json --index out/blind.idx --span-id f                     # 退出码 2（歧义）
```

测试环境：Linux aarch64 / Python 3.13.13 / tiktoken cl100k_base。
