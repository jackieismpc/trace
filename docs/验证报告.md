# tracelens 验证报告

> 全部数据由仓库内脚本/命令实测产出，可原地复现（见文末）。
> 报告日期：2026-07-23。真实 Agent 盲测环境：Linux aarch64 / Python 3.13.13 /
> tiktoken cl100k_base；性能与确定性自验：macOS 26.5.2 / Apple Silicon / Python 3.13。

验证分三条独立证据线：**真实 Agent 盲测**（把 LLM 放进回路，第一节）、**信息可达性
自验**（不调 LLM 的实验/对照组，第二节）、**工具正确性与性能**（第三至六节）。

---

## 一、真实 Agent 盲测（把 LLM 放进回路）

第二节的两个自验 demo 刻意不调用任何 LLM——它们只论证「根因证据是否落在 Agent 能拿到
的那部分数据里」。本节补上另一环：**证据可达之后，一个真实的、事先不知道答案的 LLM，
能不能只凭骨架 + 按需展开把根因查出来。**

**盲测协议**（保证结论不是「模型碰巧猜对」）：根因由
[`scripts/blind_bug_fixture.py`](../scripts/blind_bug_fixture.py) 用 `os.urandom` 在 4 个
「静默失败」原型间随机选定，答案当场密封；测试设计者在被测 Agent 交卷前不看骨架、不开封。
被测者是两个**冷启动的 Claude Sonnet 子 Agent**，除各自拿到的文件外对 bug 一无所知。本次
抽中：第 20 轮 `load_dataset` 报 `KeyError: config key 'FINANCE_PATH' is not set`，被
`config_loader` 吞掉标成 OK。

**被测 Trace**：411 span、3,972,199 字节、全文 **1,154,189 token**，根因 span 在第
3,129,145 字节；**128K 窗口只装得下全文的 11.1%**，且装的是最没用的头部几轮巨型 prompt。

**结果**——两组唯一变量是「是否用 tracelens」，同一个模型：

| 维度 | 实验组（16KB 骨架 + expand） | 对照组（原始 JSON 截断进 128K 窗口） |
| --- | --- | --- |
| 拿到的拓扑 | 100%（411→29 存活+占位，节点数守恒） | 14%（57/411），且只有头部 |
| 看得到 ERROR 节点 | 是（唯一 1 个，一眼可见） | 否（窗口内 0 个 ERROR） |
| 根因定位 | **精确命中** span_id + 错误原文 + 传播链 | **无法定位**，根因在窗口外 |
| 数据足迹 | 13,078 token（窗口的 10.2%、全文的 1.13%） | 148,997 token 填满窗口仍失败 |
| 输出可信度 | 有据可查、可逐条复核 | 诚实判定「证据不足」（未幻觉） |

实验组的诊断经**独立复跑核对**，逐字段命中密封答案：根因 span `f61c23…`、错误原文与
错误码逐字一致、外层 `config_loader` 吞错、第 20 轮触发、传播链（内层 ERROR→外层标 OK
把错误当结果→进入每轮 prompt→编造答案）全部命中。它全程只读骨架、按需 `expand`，未直接
读原始大文件。

对照组失败且失败模式在数据层面可直接判定：根因在第 313 万字节，窗口在 51 万字节处就截断了。
它没有幻觉，而是**正确诊断出自己的失败模式**——这恰说明幻觉风险来自「证据缺失又被迫作答」，
而 tracelens 消除的正是「证据缺失」这一前提。

一个副产品发现：因规则对 ERROR 节点 `keep` 全文，根因那行**直接印在 16KB 骨架里**，
且紧挨着状态为 OK 的兄弟节点 `config_loader`——「子 ERROR / 兄 OK」这个结构信号不在任何
一段文本里，它在结构里，任何「截断前 N 字节」的方案都拿不到。

> 诚实标注：这是**一个**随机实例上的**一次**盲测（抽中 `missing_config_key` 原型）。要给出
> 「成功率」需在多种子、四原型上各跑多次统计——生成器每次运行自动换种子，已支持。本次价值在于：
> 在一个设计者事先不知答案的实例上，跑通了「真实 LLM + 骨架 + expand」的完整闭环。

## 二、信息可达性自验（不调 LLM）

用确定性的 demo fixture（[`make_demo_fixture.py`](../scripts/make_demo_fixture.py)，植入 SQL
表名写错、错误被吞的 bug）从**可达性**这一维补充第一节，且不依赖任何模型的发挥：

| 指标 | demo fixture | 骨架（demo_rules.toml） |
| --- | --- | --- |
| span 数 / 体积 | 411 / 3.8 MB（payload 占 99.9%） | 存活 29，占位守恒 |
| token（工具估算） | ~917,000 | 3,713（窗口的 2.9%） |
| 体积占原文件 | — | 16 KB / **0.41%** |

- **实验组**（`demo_investigate.py`）：读骨架即命中唯一 ERROR 节点，注意到同层 `tool_executor`
  为 OK → 判断错误被吞；`expand` 取回根因（`relation "revenue_q3" does not exist` / `42P01`）
  与下游 prompt，全程约 3,963 token（窗口的 3.1%）。
- **对照组**（`demo_control.py`）：原始 Trace 截断进 128K，只装下前 553,709 字节（全文 13.9%）、
  60/411 span，**唯一的 ERROR 落在窗口外**。失败模式可在数据层面直接判定。

命题的正确表述不是「压缩了 99.6%」，而是：**原始 Trace 只装得进窗口的 ~14% 且 Agent 无法选
装哪部分；用工具后 Agent 拿到 100% 拓扑 + 自选关键细节，只占窗口 3%。** 关键在「无法选择」——
截断是被动的，索引 + 按需展开是主动的。

## 三、工具正确性与边界

四条设计承诺逐条实测，全部通过：

- **① 字节级一致（构造性）**：`expand` 输出即原文件切片 `buf[off:off+len]`，无解析/再序列化。
  独立复跑根因 span 的 `expand`，其 blake2b 与原文切片完全一致。
- **② 宁可失败不喂错（退出码 3）**：篡改原文件 1 字节后 `expand` 立即以退出码 3 报错，打印
  索引摘要 vs 当前摘要不一致，而非返回错位切片。
- **③「没找到」与「数据坏了」可区分（退出码 2）**：不存在的 span_id → 码 2；歧义短前缀 → 码 2
  并列出候选。
- **④ 硬保护**：尽管规则激进折叠了数百节点，根因 span、外层封装、所在轮、根节点仍全部保留
  在骨架中——根 + ERROR 路径由代码保证，不交给配置。

字段级 `expand --field "$.attributes['mlflow.spanOutputs']"` 精确取回单字段字节，无需整 span。

## 四、渲染形态 token 对比

同一份骨架、三种渲染（tiktoken cl100k_base 实测）：

| 形态 | 字节 | token | 相对 tree |
| --- | --- | --- | --- |
| tree | 16,247 | **5,467** | — |
| json | 33,314 | 9,512 | +74% |
| md | 16,390 | 5,933 | +9% |

tree 比 json **省 43% token**。给 Agent 读用 tree 是划算的默认，需机器再解析时才用 json。

## 五、性能实测

`bench_pipeline.py 200`，200 MB 合成 MLflow Trace（25,878 span）：

| 阶段 | 耗时 | | 验收线 | 实测 |
| --- | --- | --- | --- | --- |
| 扫描 | 0.24 s（**833 MB/s**） | 扫描吞吐 | ≥ 200 MB/s | ✅ 833 |
| 元数据解析 | 1.45 s | 1 GB 全流程 | ≤ 120 s | ✅ 16 s（线性外推） |
| 剪枝+截断 | 0.48 s | 堆内存峰值 | ≤ max(256MB, 2×最大 span) | ✅ 83.7 MB |
| 渲染 / 建索引 | 0.06 / 0.15 s | | | |
| **全流程** | **3.20 s** | | | |

核心性质：mmap 只读 + 逐 span 解析用后即弃，使堆占用与「最大单个 span」成正比、而非与文件
大小成正比（200 MB 文件堆峰值仅 83.7 MB）。1 GB 是线性外推，正式验收应单独跑 `bench_pipeline.py 1024`。

## 七、与 compaction / condenser 类方案的定性对比

| | compaction / condenser | tracelens |
| --- | --- | --- |
| 是否有损 / 可逆 | 有损 / 不可逆 | 无损 / 凭 span_id 逐字节取回 |
| 是否引入模型 | 由 LLM 生成摘要 | 零 LLM，纯确定性程序 |
| 服务场景 | 进行中的会话 | 事后取证 |
| 失败模式 | 摘要可能把根因压掉且无法回头 | 索引失配 → 明确报错（退出码 3） |

两者互补：进行中的会话丢细节换继续工作是划算的；事后排查的约束正相反——证据不能有损。

## 八、局限性

见 [局限性与改进方向](局限性.md)。要点：`expand` 依赖原文件在场（会轮转时用 `--detach`
提前物化）；token 计数默认估算，装 `[tokens]` extra 才精确；`SpanKind` 启发式可能出错，
兜底是 `KindSource` 可信度标记；真实 Agent 盲测目前是单实例单次，成功率需多次统计。
