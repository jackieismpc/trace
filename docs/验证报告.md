# tracelens 验证报告

> 全部数据由仓库内脚本/命令实测产出，可原地复现（见文末「复现」）。
> 报告日期：2026-08-05。真实 Agent 盲测与真实采集环境：macOS / Apple Silicon / Python 3.13
> / opencode 1.18.13 + mydeepseek；性能与确定性自验：同机。

测试分三类数据源、三条证据线，方案见[测试方案](测试方案.md)：

1. **真实采集闭环**（opencode 插件，§一）——插件把真实会话导出为标准 MLflow `trace.json`，验证格式真实可用；
2. **信息可达性自验**（不调 LLM，§二）+ **真实 Agent 盲测**（LLM 进回路，§三）——验证「证据能否送到 Agent 面前」与「送达后能否查出根因」；
3. **工具正确性 / 渲染 / 性能 / 质量**（§四~§七）——横切校验。

## 一、真实采集闭环（opencode 插件）

采集层（方案 A）：[`opencode-plugin/`](../opencode-plugin/README.md) 监听 `session.idle`，
经 SDK 拉取真实消息/部件后组装为标准 MLflow `trace.json`。`scripts/opencode_collect_demo.sh`
一次跑通「采集 → inspect → skeleton → expand 字节级校验」。

本次实测（真实会话：`opencode run "运行 pwd 命令查看当前目录"`）：

| 项 | 结果 |
| --- | --- |
| 插件产出 | `.tracelens/traces/*.trace.json`，标准 MLflow 形态（`{"info","data":{"spans"}}`） |
| span 结构 | 1 根 `AGENT` + 2 轮 `LLM` + 1 `TOOL`（`bash: pwd`），父子关系正确 |
| `inspect` | `格式: mlflow`、span 总数/根节点正确 |
| `skeleton` | 4 span 全部保留，token 预算内渲染 |
| `expand` 字节级 | **4/4 span 取回字节均与原文逐字节一致** |

固定样本 `opencode-plugin/tests/fixtures/opencode_sample.trace.json`（插件确定性产出，含
工具 ERROR）在 CI 中做离线闭环：`tests/test_opencode_plugin_trace.py` 验证
「解析 → 骨架 → 索引 → 按 span_id 逐字节展开」，ERROR 的错误原文在 `status_message` 中可见。

## 二、信息可达性自验（不调 LLM）

用确定性的 demo fixture（`scripts/make_demo_fixture.py`，植入 SQL 表名写错、错误被吞的 bug）
从**可达性**这一维论证，不依赖任何模型发挥：

| 指标 | demo fixture | 骨架（demo_rules.toml） |
| --- | --- | --- |
| span 数 / 体积 | 411 / 3.8 MB（payload 占 99.9%） | 存活 29，占位守恒 |
| token（工具估算） | ~917,236 | 3,713（窗口的 2.9%） |
| 体积占原文件 | — | 16 KB / **0.41%** |

- **实验组**（`demo_investigate.py`）：读骨架命中唯一 ERROR 节点，注意同层 `tool_executor`
  为 OK → 判断错误被吞；`expand` 取回根因（`relation "revenue_q3" does not exist` / `42P01`）
  与下游 prompt，全程约 **3,963 token**（窗口 3.1%）。
- **对照组**（`demo_control.py`）：原始 Trace 截断进 128K，只装下前 553,709 字节（全文 13.9%）、
  60/411 span，**唯一的 ERROR（字节偏移 1,297,498）落在窗口外**。失败模式可在数据层面直接判定。

命题的正确表述不是「压缩了 99.6%」，而是：**原始 Trace 只装得进窗口的 ~14% 且 Agent 无法选择
装哪部分；用工具后 Agent 拿到 100% 拓扑 + 自选关键细节，只占窗口 3%。** 关键在「无法选择」——
截断是被动的，索引 + 按需展开是主动的。

## 三、真实 Agent 盲测（LLM 进回路）

盲测协议：根因由 `scripts/blind_bug_fixture.py` 用 `os.urandom` 在 4 个「静默失败」原型间
随机选定，答案当场密封；测试设计者在被测 Agent 交卷前不看骨架、不开封。本次被测 Trace：
411 span、3,986,453 字节（3.80 MB），根因 span 在字节 2,800,937，**128K 窗口（512,000 字节）
装不下，且根因落在窗口外**。

| 维度 | 实验组（16KB 骨架 + expand） | 对照组（原始 JSON 截断进 128K 窗口） |
| --- | --- | --- |
| 拿到的拓扑 | 100%（411→29 存活+占位，节点数守恒） | 14%（57/411），且只有头部 |
| 看得到 ERROR 节点 | 是（唯一 1 个，一眼可见） | 否（窗口内 0 个 ERROR） |
| 根因定位 | **精确命中** span_id + 错误原文 + 传播链 | **无法定位**，根因在窗口外 |
| 数据足迹 | 13,078 token（窗口 10.2%、全文 1.13%） | 148,997 token 填满窗口仍失败 |
| 输出可信度 | 有据可查、可逐条复核 | 诚实判定「证据不足」（未幻觉） |

> 诚实标注：这是**一个**随机实例上的**一次**盲测。要给出成功率需多种子、四原型各跑多次
> 统计——生成器每次运行自动换种子，已支持。本次价值在于：在设计者事先不知答案的实例上，
> 跑通了「真实 LLM + 骨架 + expand」的完整闭环。

## 四、工具正确性与边界

四条设计承诺逐条实测，全部通过：

- **① 字节级一致（构造性）**：`expand` 输出即原文件切片 `buf[off:off+len]`，无解析/再序列化。
  独立复跑根因 span 的 `expand`，其 blake2b 与原文切片完全一致。
- **② 宁可失败不喂错（退出码 3）**：篡改原文件 1 字节后 `expand` 立即以退出码 3 报错，打印
  索引摘要 vs 当前摘要不一致，而非返回错位切片。
- **③「没找到」与「数据坏了」可区分（退出码 2）**：不存在的 span_id → 码 2；歧义短前缀 → 码 2
  并列出候选。
- **④ 硬保护**：尽管规则激进折叠了数百节点，根因 span、外层封装、所在轮、根节点仍全部保留
  在骨架中——根 + ERROR 路径由代码保证，不交给配置。

字段级 `expand --field "$.attributes['mlflow.spanOutputs']"` 精确取回单字段字节，无需整 span。

## 五、渲染形态 token 对比

同一份骨架、三种渲染（tiktoken cl100k_base 实测）：

| 形态 | 字节 | token | 相对 tree |
| --- | --- | --- | --- |
| tree | 16,247 | **5,467** | — |
| json | 33,314 | 9,512 | +74% |
| md | 16,390 | 5,933 | +9% |

tree 比 json **省 43% token**。给 Agent 读用 tree 是划算的默认，需机器再解析时才用 json。

## 六、性能实测

`bench_pipeline.py 200`，201.7 MB 合成 MLflow Trace（25,878 span）：

| 阶段 | 耗时 | | 验收线 | 实测 |
| --- | --- | --- | --- | --- |
| 扫描 | 0.24 s（**826 MB/s**） | 扫描吞吐 | ≥ 200 MB/s | ✅ 826 |
| 元数据解析 | 1.45 s | 1 GB 全流程 | ≤ 120 s | ✅ 16 s（线性外推） |
| 剪枝+截断 | 0.48 s | 堆内存峰值 | ≤ max(256MB, 2×最大 span) | ✅ 83.7 MB |
| 渲染 / 建索引 | 0.05 / 0.16 s | | | |
| **全流程** | **3.22 s** | | | |

核心性质：mmap 只读 + 逐 span 解析用后即弃，使堆占用与「最大单个 span」成正比、而非与文件
大小成正比（201.7 MB 文件堆峰值仅 83.7 MB）。1 GB 是线性外推，正式验收应单独跑
`bench_pipeline.py 1024`。

## 八、与 compaction / condenser 类方案的定性对比

| | compaction / condenser | tracelens |
| --- | --- | --- |
| 是否有损 / 可逆 | 有损 / 不可逆 | 无损 / 凭 span_id 逐字节取回 |
| 是否引入模型 | 由 LLM 生成摘要 | 零 LLM，纯确定性程序 |
| 服务场景 | 进行中的会话 | 事后取证 |
| 失败模式 | 摘要可能把根因压掉且无法回头 | 索引失配 → 明确报错（退出码 3） |

两者互补：进行中的会话丢细节换继续工作是划算的；事后排查的约束正相反——证据不能有损。
